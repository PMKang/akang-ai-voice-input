# 弱网环境转写降级设计

状态：已确认，待实现。

## 目标与首期边界

弱网环境可以牺牲实时出字速度，但不能因为实时 WebSocket 延迟、乱序、超时或断线要求用户重新说一遍。

首期完整降级仅覆盖当前豆包实时模型 `doubao-seed-asr-2-0`：它可以复用用户已配置的豆包 API Key 调用豆包录音文件识别。用户选择百炼实时模型时，本次只提供弱网提示和实时通道修复，不承诺文件识别兜底；设置页需要明确显示该能力差异。后续为百炼接入对应文件模型后才能扩大承诺。

成功标准：

- 正常网络继续边说边出字，不增加可感知等待。
- 使用豆包实时模型时，从音频转换后、语音门控前保存连续的 16 kHz 单声道 PCM，保留语音、停顿和断句时间。
- 检测到服务端响应明显变慢时，不指责用户网络，只说明转写需要更多时间。
- 实时结果缺失或链路失败时，停止录音后自动使用完整录音做文件识别。
- 完全断网时保留待处理任务，网络恢复后自动继续；用户不需要重新录音。
- 同一会话最多交付一次，不会因实时迟到回调、重试或应用重启重复粘贴和重复写历史。
- 首期单次录音最长 5 分钟；4 分 30 秒提示即将结束，5 分钟自动停止并开始转写，以保证 WAV 和 Base64 请求均处于稳定大小范围。

## 方案比较

### 方案 A：只保留实时识别并增加提示

改动最小，但只能解释等待，无法解决会话超时、结果不完整和断线丢失。不能满足“不用重说”的核心目标。

### 方案 B：录音中途切换另一条实时模型

可能恢复实时预览，但另一条云链路同样受弱网影响，而且模型间的断句、标点和增量语义不同。中途拼接容易重复或漏字，不作为首选。

### 方案 C：实时快通道 + 本地完整录音 + 文件识别兜底

正常时使用当前流式 ASR；同时在本地落盘门控前的连续音频。实时链路异常时不在录音中途换模型，用户停止后用完整录音重新识别。该方案兼顾正常速度和弱网完整性，作为推荐方案。

端侧识别可在后续作为弱网草稿预览增强，但不属于首期可靠性闭环。

## 用户体验

### 正常录音

悬浮条继续显示声波和实时文字。用户无需知道本地还保存着临时音频。

### 响应变慢

`RealtimeHealthTracker` 使用单调时钟，而非系统墙上时间。满足以下任一条件时标记 `slow`：

- 已持续采集有效语音，但从首个有效 PCM 起 5 秒仍未收到第一段非空转写；用户停止说话时暂停该计时。
- 最近一次有效语音已发送，且其后持续产生并发送有效语音，但 8 秒未收到更新的服务端识别结果；纯停顿不触发。
- 待发送队列代表的音频时长超过 2 秒并持续 3 秒。阈值集中在策略类型中配置，实测后可调整。
- WebSocket 建连或服务端会话 ready 超过 5 秒。

协议错误、连接错误和服务端明确超时直接标记 `failed`，不再称为 `slow`。

展示文案：

> 当前网络响应较慢，转写可能比平时需要更长时间，请耐心等待。

声波和计时继续运行，用户可以继续说。收到新文字后可移除提示；`slow` 只影响提示，不自动决定文件兜底，避免一次短暂延迟造成额外识别成本。

### 停止录音

只有满足以下任一可靠性条件时才启动文件兜底：

- 实时状态为 `failed`；
- 没有非空最终结果；
- 停止时仍有未确认发送完成的音频队列；
- 实时协议没有给出本会话的最终完成事件。

状态仅为 `slow`、但所有音频已按序发送并收到正常最终完成事件时，仍使用实时结果。

- 需要兜底：悬浮条进入“正在完成转写”，继续展示 `当前网络响应较慢，转写可能比平时需要更长时间，请耐心等待。`
- 文件识别完成：交付完整结果并删除临时音频。
- 当前无网络：展示 `录音已保存，将在网络恢复后自动完成转写。`，任务进入待重试队列。
- 文件识别不可恢复失败：保留任务并明确提供复制已有实时草稿、手动重试和删除录音三个操作，不自动写入疑似残缺文字。

## 数据流

```text
麦克风输入
   └─> 转换为连续 16 kHz / mono / PCM16
         ├─> 本地 WAV（门控前，保留完整时间线）
         └─> 语音门控 ──> 实时 ASR ──> 实时预览 / 健康事件

停止录音
   ├─ 实时最终事件完整 ──> 交付协调器 ──> 写入文字 ──> 删除 WAV
   └─ 实时失败或不完整 ──> 文件 ASR ──> 交付协调器 ──> 写入文字 ──> 删除 WAV
                                  │
                                  └─ 网络不可用 ──> 持久化任务并自动重试
```

## 会话与任务状态机

每次录音在开始前生成不可复用的 `sessionID`；创建文件兜底任务时生成持久化 `taskID`。实时客户端、文件客户端、超时任务和交付操作的所有回调都必须携带并校验 ID。旧会话回调不得修改当前 UI 或交付结果。

```text
recording
   ├─ stop + 实时健康 ─> awaitingRealtimeFinal
   │                        ├─ final ─> readyToDeliver
   │                        └─ fail/timeout ─> fallbackQueued
   └─ 实时在录音中失败 ─> recordingFallbackOnly ─> fallbackQueued

fallbackQueued ─> submitting ─> readyToDeliver ─> delivered
      │                 ├─ retryable error ─> fallbackQueued
      │                 └─ terminal error ─> needsUserAction
      └─ 24h 到期 ─> expired

needsUserAction ── 手动重试 ─> fallbackQueued
needsUserAction/fallbackQueued/submitting ── 用户删除 ─> cancelled
```

规则：

- listening 期间实时失败且 `archiveAvailable == true` 时，只断开实时链路并进入 `recordingFallbackOnly`，不得停止麦克风、清除焦点或隐藏录音 UI。
- listening 期间实时失败且 `archiveAvailable == false` 时进入 `unrecoverableWhileRecording`，立即停止录音并提示“两条转写通道均不可用，本次内容无法继续可靠记录”；不得展示“仍在录音”或“录音已保存”。
- fallback 一旦进入 `submitting`，迟到的实时 final 只记诊断并忽略。
- `delivered`、`expired`、`cancelled` 是单一终态；终态任务拒绝任何后续回调。
- 自动重试 6 次耗尽后进入 `needsUserAction`；用户手动重试会开启新一轮单次提交，但不会重置 24 小时到期时间。
- 用户删除时先取消正在进行的请求并持久化 `cancelled`，再删除 WAV；删除完成后移除 journal。
- 同一时间最多有一个交付协调器处理某个 `sessionID/taskID`。

## 组件设计

### `SessionAudioArchive`

负责把音频转换器产生、尚未经过 `AdaptiveVoiceGate` 的连续 16 kHz、单声道、16-bit PCM 顺序写入临时 WAV。实时流仍继续使用门控后的 PCM，两个消费者不可共用会丢弃静音的回调。

- 会话开始创建权限为 `0600` 的随机 UUID 文件；目录权限为 `0700` 并排除系统备份。
- 停止时补齐 WAV 头并原子关闭文件。
- 写盘失败或磁盘空间不足时立即标记“无文件兜底能力”，但实时录音可继续；UI 不得承诺录音已保存。
- 4 分 30 秒显示“为确保内容完整，本次录音将在 30 秒后自动转写”；5 分钟自动调用现有停止流程。5 分钟连续 PCM 约 9.6 MB，Base64 后约 12.8 MB，低于官方建议尽量控制在 20 MB 内的上传规模。
- 正常完成后删除；待重试时保留。
- 启动时清理无任务引用的孤立 WAV，并恢复有有效 journal 的任务。若 journal 已是 `delivered`、`expired` 或 `cancelled`，不得再交付或重试，但必须幂等删除其引用的 WAV，随后删除 journal；文件已经不存在也视为清理成功。

### `RealtimeHealthTracker`

只根据可观测事件判断当前会话是否健康：首个/最近有效 PCM 时间、实际发送完成时间、队列音频时长、最后服务端文字时间、连接 ready、协议完成事件和错误。`NWPathMonitor` 仅作为“彻底离线”的辅助信号，不能单独代表网络质量。

状态为 `healthy`、`slow`、`failed`。`slow` 只驱动提示；停止时由明确的发送确认和最终完成事件决定是否兜底。

### `RecordingFileTranscriptionClient`

首期仅在当前会话使用豆包模型且豆包文件识别资源已开通时启用，调用[豆包大模型录音文件极速版识别 API](https://www.volcengine.com/docs/6561/1631584?lang=zh)。设置页的能力检查必须在录音前显示“文件兜底可用/不可用”，不可在失败后才要求新凭证。

接口合同固定为：

- `POST https://openspeech.bytedance.com/api/v3/auc/bigmodel/recognize/flash`，一次请求同步返回结果，不使用 submit/query 轮询。
- 新版控制台鉴权头：`X-Api-Key` 使用现有 Keychain 中的豆包 API Key；`X-Api-Resource-Id` 固定为 `volc.bigasr.auc_turbo`；`X-Api-Request-Id` 使用持久 `taskID`；`X-Api-Sequence` 固定为 `-1`。
- 请求体：`user.uid` 使用稳定的本机匿名 ID，`audio.data` 为本地 WAV 的 Base64，`request.model_name` 为 `bigmodel`。
- 成功以响应头 `X-Api-Status-Code == 20000000` 为准，正文取 `result.text`；同时记录不含正文的 `X-Tt-Logid` 供诊断。
- 官方支持 WAV、MP3、OGG OPUS，单文件不超过 2 小时和 100 MB，并建议二进制上传尽量控制在 20 MB 内。首期进一步限制为 5 分钟 WAV，不做压缩或分段。
- 当前 App 只支持新版控制台的单 API Key 形态。旧版控制台需要 `X-Api-App-Key + X-Api-Access-Key`，首期不支持；设置页需明确提示用户使用新版 API Key。
- 文件识别资源 `volc.bigasr.auc_turbo` 必须单独开通。模型连接测试新增一次不含用户音频的能力校验；未开通时标记“实时可用，文件兜底不可用”。
- 请求超时 60 秒；进入取消或应用退出时取消 URLSession task。同步接口不返回 provider task ID，因此 journal 不保存该字段，客户端仍以 `taskID` 去重交付。

错误分类：

- 网络错误和 5xx：可重试。
- 429：尊重 `Retry-After`。
- 鉴权、未开通资源和其他确定性 4xx：进入 `needsUserAction`，不自动重试。
- 文件过大或格式错误：进入 `needsUserAction`。

### `PendingTranscriptionStore`

用原子 journal 保存：`taskID`、`sessionID`、WAV 路径、创建时间、状态、重试次数、下次重试时间和是否已有实时草稿。不得保存 API Key、焦点对象或转写正文。

重试只用于网络/5xx/429，使用带 jitter 的指数退避，默认 5 秒、30 秒、2 分钟、10 分钟、30 分钟，上限 6 次；网络恢复事件只负责唤醒调度器，不能绕过 `nextRetryAt` 或并发启动重复请求。应用退出取消进行中的请求，下一次启动按 journal 恢复。

任务从创建起最多保存 24 小时，到期进入 `expired` 并自动删除 WAV；到期后不再提供手动重试。应用需要在删除前发出本地通知或应用内失败记录。

### `TranscriptionDeliveryCoordinator`

自动交付采用 at-most-once 语义：

1. 文件识别得到结果后，先将结果以 `taskID` 唯一键原子写入历史记录，并把任务 journal 更新为 `readyToDeliver`。
2. 仅当前进程、原会话的内存焦点上下文仍有效时尝试自动写入输入框。
3. 写入成功后标记 `delivered`，再删除 WAV 和任务 journal。
4. 写入失败时将文字放入剪贴板并展示现有剪贴板兜底；仍标记 `delivered`，不自动再次粘贴。
5. 应用若在 `readyToDeliver` 状态崩溃或重启，恢复后只把已去重的历史结果放入剪贴板并通知，绝不向新焦点自动粘贴。

`HistoryItem` 增加可选 `taskID` 并建立唯一去重。焦点上下文只存在于当前进程、当前录音会话内存中；持久化任务加载后一律以历史记录和剪贴板为目的地。

## 结果选择

不把实时文本和文件文本做字符级拼接：

- 实时健康且收到完整最终事件时使用实时最终结果。
- 触发文件兜底后，以文件识别结果整体替换实时预览，并忽略迟到实时 final。
- 文件识别最终失败但已有非空实时草稿时，只提供用户主动复制，不自动静默写入疑似残缺文本。

## 隐私与清理

- 临时录音仅保存在应用支持目录，不进入诊断报告、历史正文导出或遥测。
- 文件权限 `0600`、目录权限 `0700`，目录排除系统备份。
- 正常完成后立即删除；待重试最长保存 24 小时，到期自动删除。
- 应用提供“一键清除待转写录音”；清除先取消请求、落 journal 终态，再删除文件。
- 诊断只记录 ID 的短哈希、字节数、持续时间、状态和错误类别，不记录音频、转写正文或凭证。

## 可测试架构

新增组件通过协议和构造注入接入协调器：`AudioArchive`、`RealtimeClient`、`FileTranscriptionClient`、`PendingStore`、`OutputSink`、`NetworkStatusProviding`、`MonotonicClock`、`RetryScheduler` 和 `FileSystem`。生产环境提供真实实现，测试使用内存实现、虚拟时钟和确定性调度器。避免继续把新逻辑直接固化到全局静态输出器和不可替换的 `AppState` 依赖中。

测试范围：

- 门控前连续 PCM 写入 WAV，门控后的 PCM 仍按序进入实时队列；静音段保留且不触发实时发送。
- WAV 头、采样率、声道、持续时间和文件权限正确。
- 持续说话时 5 秒首字延迟触发提示；纯静音和说话后的长停顿不误报。
- 队列积压阈值、连接 ready 延迟和单调时钟行为可确定测试。
- 实时完整完成不调用文件识别；slow 后恢复且最终事件完整也不调用。
- 实时超时、断线、协议错误、未发送完毕和空结果调用文件识别。
- 迟到实时回调、并发网络恢复事件和旧 session 回调不会重复交付。
- 每个崩溃点恢复后历史按 `taskID` 去重，跨重启不自动粘贴。
- 写盘失败、磁盘满、孤立文件、手动清理和 24 小时过期正确处理。
- 实时失败与归档失败同时发生时立即停止，且绝不显示“仍在记录/已保存”。
- 4 分 30 秒提示、5 分钟自动停止和文件大小上限正确。
- `needsUserAction` 手动重试以及 `cancelled` 终态不会留下请求或音频文件。
- 分别在 `delivered`、`expired`、`cancelled` 终态已落盘但 WAV 尚未删除时模拟崩溃，重启后均只执行幂等清理，不交付、不重试。
- 网络/5xx、429、4xx 和鉴权错误遵循各自重试规则。
- 诊断与持久化元数据不包含凭证、焦点对象和转写正文。

## 首期不做

- 录音中途切换实时模型；
- 实时结果与文件结果的字符级合并；
- 内置 Whisper 等额外本地模型；
- 用户手动选择“实时或文件模式”；
- 为仅配置百炼凭证的会话承诺文件识别兜底。

这些能力只有在豆包双通道闭环经过弱网实测后再评估。
