# 自在说产品演进日志

这不是发布说明，也不是功能清单。它记录产品从真实使用中的别扭瞬间出发，如何逐步形成设计和工程决策；后续可作为文章、复盘和需求讨论的原始素材。

## 2026-08-09｜一条悬浮语音条，为什么会挡住用户工作

### 触发场景

语音输入进行中，用户在另一个应用中打开模型切换菜单。自在说的语音输入悬浮条固定在屏幕下方，刚好遮住了菜单。问题不是语音识别本身，而是一个本来负责帮助输入的界面，抢占了用户正在操作的空间。

### 先被推翻的假设

最初容易想到“当模型菜单打开时，悬浮条自动避让”。但这是假设自在说知道别的应用打开了什么控件、控件在哪儿。作为跨应用悬浮层，它通常并不能可靠取得这些信息；把这个能力当作解决方案并不现实。

### 当前判断

可拖动不是可有可无的附加能力，而是跨应用场景的主要解法。用户必须能在当下把语音条移开，而不用依赖宿主应用的结构。

但只有拖动还不够：首次遮挡时，用户可能还没意识到能拖。因此组件还需要提供主动让位的层级，而不是只提供一种固定长条。

### 形成中的交互方案

组件根据用户操作在三种状态之间切换，而不是在设置页提供“横条、竖条、圆球”的复杂外观选择：

1. **展开横条**：录音时展示状态、波形、较完整的实时文字与时长；左侧点阵是明确的拖动把手。
2. **微字幕胶囊**：用户主动收起后，保留动态波形、最近一段短文字和展开控件。短文字约 10–16 个字，以短语替换和淡入淡出更新，不使用跑马灯。
3. **贴边圆球**：进一步让位时只保留圆球；默认可向屏幕内侧伸出一行“字幕尾巴”，需要彻底让位时再缩回。

拖动结束后吸附至屏幕边缘或角落，并记住位置。竖条没有进入当前方案：它对实时文字不友好，也没有比胶囊显著更节省空间。

### 一个看似小、实际重要的反馈问题

如果收起后只留下波形，用户知道麦克风还开着，却不知道“有没有听到”“文字有没有进来”。因此收起状态不能完全无文字。

文字也不能和展开态一样完整滚动：它会重新占据空间，并可能在屏幕共享时泄露内容。当前取舍是：默认显示最新短语，同时提供“收起时显示实时文字 / 仅显示录音状态”的隐私开关。

波形需要真实跟随声音：说话时随音量起伏，停顿时降到低振幅，处理转写时切换为流动状态；不能用一直夸张的呼吸光效抢占用户注意力。

## 2026-08-09｜长静音不是用户停止，但连接可能已经停止

### 观察

使用过程中，用户有时仍在一次语音输入会话中，但中途长时间不说话或停顿后，再继续说会发现输入已经断掉。

### 已确认的工程事实

- 本地音频门控会过滤静音，不向服务端发送静音 PCM，以避免环境噪声进入识别。
- Fun-ASR 分支已每 5 秒发送一小段静音 PCM 保活。
- 默认 Qwen Realtime 分支没有同等保活逻辑。
- 百炼文档说明：连续 60 秒没有服务端可见消息时，WebSocket 可能以 `ResponseTimeout` 主动断开。

### 尚未确认的部分

真实用户的每次断开是否都属于这条 60 秒路径，尚未用运行日志验证；也可能包含网络波动或音频设备状态变化。不能仅凭代码推测就宣布已经修复。

### 下一步

先记录最后一次音频发送时间、最后一次服务端消息、关闭/错误摘要；然后为 Qwen 分支实现并验证协议允许的保活机制，覆盖“静音超过 60 秒，再继续说话”的回归测试。

## 2026-08-09｜第一版交互落地

### 已实现

- 悬浮窗从固定的底部横条改为三态：展开横条、微字幕胶囊、贴边圆球。
- 展开态和胶囊态都有明确拖拽把手；圆球本身也可以拖动。
- 松手后按屏幕左右侧及上、中、下三个高度吸附，并将位置持久化；下次录音在同一停靠位置出现。
- 胶囊显示实时声波、录音时长和最多约 16 个字的最新文字；圆球可显示一行字幕尾巴。
- 新增“收起时显示实时文字”开关，用于屏幕共享或隐私场景。

### 验证

项目的 Swift 测试新增了停靠位置计算与持久化覆盖；全部 48 项测试通过（其中本地 WebSocket 集成测试按既有约定跳过）。应用包已重新构建并实际启动。

### 尚待真实体验确认

拖动把手的命中范围、字幕尾巴的宽度，以及贴边圆球的默认停靠高度需要在日常跨应用操作中体验后再调。这里不能用静态 mockup 替代真实判断。

## 2026-08-09｜让下一次闪退和静音断连留下证据

### 本地崩溃诊断

应用此前只有本次运行内存中的诊断。现在每个脱敏事件都写入 Application Support 下的容量受限环形日志；应用正常退出时写入完成标记。下次启动如果没有读到这个标记，会提示“上次未正常退出”，并保留退出前的诊断供复制。

这不是宣称已经抓住所有 macOS 崩溃堆栈。强制退出、信号终止和 Swift 运行时崩溃未必能安全地执行一个崩溃回调；本方案可靠地解决的是“下一次启动时知道上一轮没正常结束，并能拿回它最后的运行上下文”。

日志记录启动、录音状态、音频引擎配置变化、网络可用性变化和 Realtime 错误摘要，但不记录 API Key、Workspace ID、原始音频或转写正文。

### 静音保活

默认 Qwen Realtime 分支此前会在本地过滤静音后完全停止发送音频；现在每 15 秒仅在仍在录音、且没有真实音频时，发送一小段零值 PCM。它使用的是官方手动模式明确支持的 `input_audio_buffer.append`，而不是猜测一个服务端未文档化的心跳 JSON。

停止录音后保活立即终止；断连时诊断会记录距离最后一次音频发送和最后一次服务端消息的时长。下一次真实复现若仍出问题，就能区分“会话被空闲关闭”“网络中断”与“音频链路异常”。

## 2026-08-09｜“可以拖”不等于“用户拖得动”

### 真实反馈

第一版虽然有拖动把手和贴边按钮，但实际操作暴露出更基础的问题：把手的命中区太小，拖动时悬浮窗会闪动、跟手慢；贴边需要额外点击，既不容易发现，也没有比普通缩小状态形成足够明显的差别。

### 调整

- 拖动把手改用 macOS 原生窗口拖拽，而非在 SwiftUI 手势的每一个采样点重设窗口坐标。这是为了解决闪动和滞后，不是单纯换一个图标。
- 把手的可点击区域扩大；鼠标悬停时，点阵变为带蓝色反馈的“拖动”提示，让人知道这里可以按住移动。
- 展开态的动作明确标为“收起”，不再把“收起 / 最小化 / 贴边”混成一个概念。
- 取消独立的“贴边”按钮。用户把组件拖到屏幕外沿后松开，才自动变成贴边球；普通拖动松手仍只是吸附定位。这样“贴边”是一个空间动作，而不是又一个难懂的模式开关。

### 仍需体验验证

边缘触发阈值暂定为 56 pt。它需要在真实显示器、多屏和不同缩放比例下继续调整：阈值过小会难触发，过大又会让用户误触发缩成球。

### 第二次调整：文字应在需要理解时出现

“缩小”这个词没有准确表达动作，改为“收起”。但文字也不应该始终占据展开条的空间：静止时保留减号，鼠标移入后出现蓝色底并平滑展开“收起”。这让图标保持安静，同时在用户需要判断它做什么时给出明确答案；交互语言与拖动把手的悬停提示一致。

## 2026-08-10｜“记住位置”不该等于“每次跑到右侧”

### 发现

第一版把“记住位置”实现为左/右边缘的吸附预设，因此一次使用后，下一次打开可能出现在右侧中部。这并不是用户想要的记忆：首次启动希望是底部居中；主动移动后，才应保留用户放下的位置。与此同时，用户最后选择的是展开还是收起，也不该在下一次快捷键唤起时被强制重置。

### 新规则

- 没有主动放置过时，展开和收起都从底部居中出现。
- 主动拖放后，记录窗口中心相对于屏幕的比例位置，而不是记录某个屏幕的绝对像素或一个左右停靠标签。
- 展开条和收起胶囊尺寸不同，但会围绕同一个记忆中心切换，避免状态切换后横向跳位。
- 最后一次的展开、收起或贴边形态会被记住，并在下一次录音时恢复。

旧版仅包含“左/右侧”信息的偏好不再沿用，避免历史状态继续把新会话带到右侧。

### 实现复核：保存与状态切换是两件事

后续真实体验发现，坐标虽然在拖放后已经写入，但录音、处理、收起之间仍会各自重新计算窗口位置，视觉上像“位置没有记住”。修正为两条独立规则：拖放完成和窗口隐藏前都保存一次；状态切换只围绕当前窗口中心改变尺寸，不参与位置决策。这样处理提示和收起形态才能与用户拖放后的锚点保持相对静止。

## 2026-08-09｜“偶发闪退”必须先留下证据

### 观察

用户的 Mac 上应用存在偶发闪退，但目前没有稳定复现步骤，也没有可查看的本地崩溃上下文。

### 决策

不在没有堆栈和复现条件时猜测修复。先补一份本地持久化、容量受限、脱敏的崩溃前诊断日志：记录启动、录音状态切换、音频设备变化、网络状态和未处理错误摘要；不记录 API Key、Workspace ID、原始音频和转写正文。

下次启动时，如果发现上次并非正常退出，应在诊断页提示并支持复制报告。这样下一次问题发生后，讨论可以从证据开始。

## 写作线索

- 一个“看起来固定在底部最顺手”的悬浮条，为什么在跨应用使用中反而成为阻碍？
- 产品设计中最危险的假设之一：默认认为自己知道其他应用的 UI 状态。
- 动效不是装饰：语音波形如何承担“正在听、正在转写、已暂停”的状态沟通。
- 从偶发问题到可修复问题，中间差的往往不是更聪明的猜测，而是一份能留下来的诊断记录。
