# 文章审校清单（未直接改正文）

以下是我建议你确认后再改的地方，按重要程度排序。

## 需要先确认的事实

### 1. “音频上传都按录音顺序排队”范围写大了

当前代码中，明确加了出站 FIFO 队列的是 **豆包实时客户端**。阿里云百炼的实时客户端没有在这次改动里做同样的队列处理。

正文目前写成“不管网络好坏，音频上传都按录音顺序排队”，读者会理解成所有模型、所有识别链路都已经这样处理。

建议改为：

> 这次也把豆包实时识别的音频上传改成按录音顺序排队。

如果文章不想点供应商，则删掉这段底层细节，只写“同时收紧了实时音频发送的顺序控制”。

### 2. “前一段发完，下一段再发”不够精确

代码等待的是 `WebSocket.send` 完成，即应用把数据交给系统 WebSocket 发送接口；它不代表前一段音频已经通过网络到达服务端或被识别完成。

建议改为：

> 前一段交给 WebSocket 发送接口后，再交下一段。

这样不把本地调用完成说成网络传输完成。

### 3. “完全断网则直接结束本次识别”要缩小承诺

当前实现只在系统明确返回“无网络”时显示“检测到断网，请连接网络后再使用”。服务端异常、DNS 异常、已建立连接后的网络中断，未必都会得到这条文案。

建议改为：

> 测试时，系统明确返回无网络，识别会结束并提示连接网络后再使用。

这与实测截图一致，也不承诺所有断链类型都能被准确判成断网。

## 建议调整的表达

### 4. “小概率弱网场景”没有数据支撑

文章没有埋点或用户反馈数据，不能确认它是小概率。

建议改成：

> 对我当时的使用场景来说，这不是每天都会碰到的问题。

或者直接删去概率判断。

### 5. “用户最难受”最好收回到作者体验

这是合理推测，但不是已验证的用户研究结论。

建议改成：

> 我自己最不舒服的不是慢几秒，而是不知道语音输入法到底还在不在工作。

### 6. “结果和预期一致”略空

可以改成更有信息量的一句：

> 7 秒时没有文字，但提示已经出现；等到 26 秒，文字开始返回，提示随之消失。

后面直接接图片即可。

### 7. 最后 AI 总结可以再具体一点

现有结尾方向是对的，但“AI 让成本低了很多”有点泛。

可考虑替换为：

> 以前发现这种问题，容易先记到需求池里。现在我可以先把它复现出来，改一个很小的点，再马上在同一台 Mac 上验证。AI 没替我想出这个问题，只是把从问题走到验证的路缩短了。

## 不建议改动的部分

- “弱网继续等待，完全断网明确停止”的产品判断足够清楚。
- 从 Chrome 联想到 Network Link Conditioner 的过程自然，保留。
- 断网提示图与弱网提示图紧跟各自文案，阅读顺序正确。
- 封面标题与正文标题一致。
